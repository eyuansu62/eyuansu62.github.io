*基于 40 万轮真实编码轨迹的分析*

长会话的 AI 编程助手迟早会撞上一堵墙：上下文窗口。当对话越来越长，系统会把历史"压缩"（compact）成一段摘要，腾出空间继续工作。

这带来一个自然的问题：**压缩之后，模型还记得自己在干什么吗？它会不会变笨？**

我们分析了三份真实数据——一份来自 [TraceLab](https://github.com/uw-syfi/TraceLab)（UW SYFI）的聚合编码轨迹集（约 35.7 万轮、4265 个会话），以及作者自己的 Codex（495 个会话）与 Claude Code（5856 个会话）原始日志——试图回答这个问题。过程中我们踩了两个方法论的坑，也得到了一些反直觉的结论。这篇文章把方法和发现都摊开讲。

## 〇、数据：三份互相印证的轨迹

| 数据源 | 规模 | 特点 | compact 检测 |
|---|---|---|---|
| **[TraceLab](https://github.com/uw-syfi/TraceLab)**（UW SYFI 聚合轨迹集） | 357,161 轮 / 4,265 会话 / 23 个模型 | 覆盖 Claude 与 GPT 两大系列；轮次级元数据（token、工具调用、is_error），**不含工具内容** | token 突降（>30% 且 >5K） |
| 作者自有 **Codex** 日志 | 495 会话 / 10,810 轮 | 含原生 `compacted` 事件与完整命令内容 | 原生事件 |
| 作者自有 **Claude Code** 日志 | 5,856 会话 | 含完整 tool_use 文件路径与 usage | token 突降 |

TraceLab 提供**跨模型的广度**（对比 23 个模型），但只有元数据；两份自有日志提供**内容深度**（命令、文件路径），能直接观测"重读补救"等行为。三者互相印证，任何单一数据的结论都需另外两个确认。

## 一、先定义"能力"：output token 是个陷阱

最直觉的做法是看 compact 前后模型"产出"的变化。我们一开始也这么做了，发现很多模型 compact 后 output token 大幅下降（claude-opus-4-8 降了 52%），于是差点得出"严重退化"的结论。

**这是错的。**

compact 前，上下文正逼近窗口上限，模型的输出往往被"撑"得虚高；压缩后上下文释放，输出变短可能只是更高效的响应。用 output token 衡量能力，等于把"上下文压力"误认成"能力"。

我们改用一组更贴近"能力"的指标，并在文中每次都明确定义：

- **错误率**：工具调用被框架标记为失败的比例（如 Bash 非零退出码）。注意这是"工具执行失败"，不等于"模型回答错误"。
- **恢复率**：出错后 3 轮内不再出错的比例——衡量模型自我纠错的能力。
- **盲目重试**：出错后重试同一个工具、但 3 轮内仍持续出错——模型陷入失败循环，这是最强的退化信号。

这套指标比 output token 可靠得多。但它仍不够，因为我们很快踩了第二个坑。

## 二、第二个坑：一个坏会话，制造了"严重退化"的假象

在 TraceLab 聚合数据里，claude-opus-4-8 的各项指标都很难看：compact 后错误率 8.8% → 21.6%，盲目重试 14% → 40%。按任何标准这都是"严重退化"。

但我们做了一次 **outlier 敏感性检查**——移除贡献错误最多的单个会话，重新计算——结论瞬间翻转：

| 指标 | 含异常会话 | 剔除后 |
|---|---:|---:|
| compact 后错误率 | 21.6% | 7.7% |
| 错误率变化 | +12.9pp | +0.1pp |
| 盲目重试 | 40% | 0% |

那个会话（`43ff8094…`）贡献了该模型 26% 的错误，单轮最多 18/21 个工具调用失败，且错误在 compact **前后**都爆发——它是一个本身就坏掉的环境，与压缩无关。小样本模型（claude-opus-4-8 只有 18 次 compact）极易被这样一个点主导。

**教训**：任何小样本结论，先做 leave-one-out 检查。一个会翻转的判定，不是发现，是假象。

做了全模型检查后，真正稳健的"compact 后正确性退化"只剩两个：claude-opus-4-7 和 gpt-5.4（它们的最错会话占比 <10%，结论不受单点影响）。而样本最大的 gpt-5.5 始终稳定。

## 三、自己的数据：正确率不退化，但模型更"费力"了

TraceLab 聚合数据只能看别人，我们还想看自己。作者自己的 Codex 和 Claude 原始日志有完整内容（命令、文件路径），能做更细的分析。

**结论一：正确率基本不退化。**

- Codex：错误率、恢复率、盲目重试 compact 前后稳定。
- Claude：错误率甚至**下降**（如 haiku 13.5% → 1.3%）。更准确地说，退化发生在 compact **之前**——上下文逼近上限时模型处于"压力"状态；压缩重置后反而更干净。compact 是减压，不是伤害。

**结论二：但模型明显更费力了。**

compact 后几乎所有数据源都出现"努力量上升"：Codex 的工具调用/轮从 9.3 翻倍到 17.3，且翻倍的几乎全是编辑操作（apply_patch 1432 → 3021）；Claude 的读取量增加约 45%。

## 四、它在"回忆"吗？不，它在重做与补救

工具翻倍，是模型在主动"回忆"上下文，还是只是普通地多干活？自有数据的内容让我们能区分。

答案是：**主要是更多编辑，辅以少量定向重读。**

- 读操作占比很小（<3%），但**性质变了**：compact 后的读操作中，约 48.5% 是重读"之前已看过的文件"（compact 前仅 7.7%）。这是真实的"丢失细节 → 重读补救"信号。
- 我们甚至抓到了现行：compact 后模型重新 `sed -n` 读已读过的 `core.py`，重新 `rg "def generate_until"` 定位一个它忘了的函数。
- 编辑方面，重改旧文件的比例只略升（59.8% → 63.5%），说明翻倍不是大规模"重做丢失的工作"，而是对同一批热点文件做更多迭代收敛。

把这些拼起来，最合理的图景是：

```
compact 丢失部分细节
   → 模型察觉，重读旧文件 / 重定位函数（补救）
   → 在信息不全下更多次编辑收敛
   → 最终结果仍正确（正确率不降）
   → 但多花了约 2 倍的步骤（效率税）
```

**正确率之所以不降，恰恰是因为模型用额外努力补偿了细节遗失。** 成果质量没退化，时间成本退化了——就像笔记被压缩的人，靠翻回原资料重查、多改几稿，保住了产出质量，但花了更多时间。

## 五、局限：看不见的才是最危险的

我们必须诚实：

- **重读只是"成功补救"的部分。** 若模型丢了细节却没察觉、不重读、直接基于摘要继续（静默遗失），telemetry 抓不到，却可能造成隐蔽错误。"正确率不降"是观测结果，不代表零风险。
- **TraceLab 聚合数据没有内容**，无法观测细节遗失，只能看间接代理；三份数据中只有自有数据能直接证实细节遗失。
- **因果不是铁证。** compact 恰发生在密集编辑阶段，"努力量上升"里有一部分是任务节奏，within-session 前后对比是合理对照但非完美。
- 结论不能推广到所有模型：TraceLab 里 opus-4-7、gpt-5.4 是真退化，补偿机制没兜住。

## 六、给实践者的启示

1. **别用 output token 衡量能力**，用错误/恢复类指标，并明确定义每个指标。
2. **小样本先做 outlier 检查**，一个会翻转的判定不可信。
3. **compact 的真实成本是效率，不是正确性**——模型用更多步骤保住结果。优化方向应是让摘要保留"热点"信息（常被重读的文件、关键决策），降低补救成本。
4. **警惕静默遗失**：可见的重读是冰山一角，压缩摘要的质量决定了看不见的风险。
